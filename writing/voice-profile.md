# My Voice Profile

This file is **mine**. It is my current best guess about how I write, to be refined as I actually publish. Every line below is a hypothesis, not a rule someone handed me. When I ship a post I'm genuinely happy with, the editor proposes a diff to this file from that post, and I approve or reject it — so the profile *learns me* over time rather than teaching me a house style.

This is the file `biostat-editor` critiques against. It is seeded from the `learning-in-public-voice` defaults, but where this file and that skill disagree, **this file wins.** The editor must treat anything here as my settled preference and flag departures from it as departures, never as errors. (See [[writing-system|writing-system.md]] and [[conventions|Vault Conventions]] §9 for the advisory-only rule.)

---

## Register (current best guess)

- First person, learning in motion. I'm a data scientist learning crop genetics in public, not an authority lecturing. The reader should watch my understanding form, including where it's still forming.
- Concrete first, concept second. I want to open on the observed thing — a number, a plot, a line of a VCF, a prediction that failed — and reach for the idea afterward.
- Honest about the edge of what I know. I'd rather say "I can derive this but I can't yet feel why" than fake confidence. Precise uncertainty is a feature.
- Mechanism over vocabulary. If I name a term, I should already have explained how it works in plain words.
- One post, one claim. If two claims are fighting for a post, it's two posts.

*To refine: my actual register may turn out warmer / drier / more technical than this. Update from real posts.*

## Opener moves I like (provisional)

1. **The thing that broke my model** — start from the moment an expectation failed.
2. **The number with a take** — a single concrete figure, pointed enough to pull the reader in.
3. **The honest confusion** — name the specific thing I misread, then resolve it.

Openers I want flagged if I drift into them: "In this post I'll…", "X is a Y that…", "Today I learned about…", "It's worth noting that…".

*To refine: note which opener actually lands with readers and lean into it.*

## Closer moves (provisional)

- End on the live question or the next experiment, not a summary.
- A closing line that names what I still don't understand is fair game and probably good.
- Flag for me: "In conclusion", "Ultimately", "To summarize", "All in all".

*To refine: do my best closers circle back to the opener, or push forward? Watch and record.*

## Sentence-rhythm habits (provisional)

- Vary sentence length on purpose. Put a four-word sentence next to a thirty-word one.
- I suspect I default to long, comma-heavy sentences when I'm unsure of a point — flag runs of same-shaped sentences so I can break them.
- Short declaratives are allowed to carry weight. I don't need to soften them.

*To refine: measure my real average sentence length from published posts and set a target band.*

## Words / phrases I avoid (provisional — edit freely)

- Vague hedges that soak a sentence in doubt: "it kind of seems like it might". If I'm uncertain, I'd rather specify the doubt ("I'm ~70% on this; the part I can't check is…").
- Filler openings: "It's important to understand", "Let's dive in".
- Negation cascades: "not the trait, not the gene, not the environment" → replace with one positive claim or one sharp contrast.
- AI-tell connective tissue ("Moreover", "Furthermore", "It is worth noting") unless it's genuinely earning its place.

*Add words I personally overuse here as I notice them in critiques.*

## Citation style (provisional)

- Default to numbered footnotes: `claim.[^3]` with `[^3]: Author — title — URL` collected at the end. I don't want parentheticals studded through the prose.
- Inline `(Author et al., 2019)` is fine when it's genuinely load-bearing in the sentence.
- Every factual specific — a dataset name, a package, a paper, a heritability figure — gets a real source. Flag any claim that reads like a fact but has no citation.

*To refine: decide whether I prefer footnotes or an end References block once I've published a few.*

## Em-dash policy (MY call)

I haven't decided yet. **Current setting: em dashes allowed, used sparingly, for a genuine break or aside — not as a default joiner.** The editor should flag overuse (more than a couple per post) as a possible tell, but must not treat any single em dash as an error. If I later decide to ban them outright, I'll change this line and the editor follows it from then on.

## How the editor should treat deviations from this file

- This file is the standard. A deviation from it is a **deviation**, surfaced as "this departs from your profile — your call," never "this is wrong."
- The editor suggests; I decide. It does not change my words unless I say "apply" / "make that change" / "rewrite this."
- When the editor thinks the profile *itself* is wrong (e.g., a move it keeps flagging is actually working for me), it should say so and propose updating this file — but only I commit that change.
- After a post I'm happy with, the editor may propose a profile update derived from that post (a new favored phrase, a confirmed rhythm, a settled em-dash decision). I approve or reject each proposed line.

This profile is a living document. Its authority comes from being *observed from my actual writing*, not prescribed. Keep it honest by updating it from real posts, not from how I wish I wrote.
